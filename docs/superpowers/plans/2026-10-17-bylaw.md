# Bylaw Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Compile a plain-English travel & expense policy into a tuned Strands Decider 2B policy pack, gate a Strands booking agent with it on AWS, and benchmark it honestly against Bedrock LLMs deciding alone.

**Architecture:** A Python package `bylaw` with four layers: (1) the pack format, a restricted expression evaluator, a Decider HTTP client and a pure `decide()` function; (2) an engine + `PolicyGate(InterventionHandler)` shared by the agent, the compiler's tuner and the benchmark, so every number measures the same code path; (3) a Bedrock-driven compiler (extract → split → author → generate cases → tune → emit); (4) a FastAPI app + React UI, deployed to one EC2 GPU instance behind CloudFront with an S3 "sleeping" fallback. Tests run against fakes; Bedrock and the real Decider only run in marked live steps.

**Tech Stack:** Python 3.12, uv, strands-agents 1.61.1, strands-decider 0.1.0 (server only), boto3 (Bedrock Converse), pydantic v2, FastAPI + sse-starlette, typer, pytest; React 18 + Vite + TypeScript + vitest; AWS EC2 g6.xlarge, S3, CloudFront, EventBridge Scheduler, IAM.

**Spec:** `docs/superpowers/specs/2026-10-17-policy-compiler-design.md`

## Global Constraints

- Declared pattern **policy**; tags `#strands-decider-2b` and `#policy`.
- Decider weights `StrandsAgents/strands-decider-2B-qwen3.5-v1-2610`; the Decider server binds `127.0.0.1` only and is never exposed publicly.
- One Decider request per gated tool call: all questions for that state go in one `POST /v1/systemone`.
- Numeric comparisons (price vs cap, days before departure, amounts) are plain-code checks, never Decider questions.
- Model-written expressions are evaluated by our whitelist evaluator; nothing generated is passed to `exec`/`eval`/`compile` of arbitrary code.
- The held-out test set is never used for tuning; it is written by a different model family than the dev-set generator, plus ~40 hand-written cases, with labels reviewed by hand.
- Every number quoted in README/article/video/UI is read from `bench/results/*/summary.json`; nothing is quoted from the Decider blog as our measurement.
- Northwind Supply Co. is fictional; no real company names, logos or policies.
- UI: no gradients, no glassmorphism, no stock "AI" iconography; serif document face, monospace for numbers. Copy passes avoid-ai-writing.
- GPU instance runs on demand only (benchmark, recording, scheduled judging window); every paid AWS action is confirmed by the user in chat first; Claude never enters credentials.
- Work on branch `feat/bylaw`; merge to `main` only on the user's say-so. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Decider server down or timing out mid-chat** → the gate fails closed: `Confirm` with "the policy check is unavailable", never `Proceed`, never a crash. Pinned in Task 6.
2. **Tool arguments missing a field a check reads, or the wrong type** (`"nightly_rate": "$240"`, no `depart_date`) → the check is *unknown* → the call is uncertain (escalate/confirm), not passed and not a 500. Pinned in Tasks 2 and 5.
3. **Long conversations past the Decider window** → the server cuts the state, which could drop the proposed call; we bound the rendered state ourselves so the proposed call and the employee profile always survive. Pinned in Task 4.
4. **Malformed or schema-invalid JSON from a Bedrock model** (compiler or baseline) → one repair retry with the validation error, then a clear error (compiler) or a recorded `abstain` counted as wrong (benchmark), never silently dropped. Pinned in Tasks 7 and 11.
5. **The agent retrying the same blocked call after a `Guide`** → after 2 guides for the same rule in one session the gate escalates to `Deny`, so the loop terminates. Pinned in Task 6.

### Task 5: Pure decision function

**Files:** Create `src/bylaw/decide.py`, `tests/test_decide.py`

**Interfaces:**
- Consumes: `Pack`, `Question`, `Violation` (Task 1).
- Produces:
  - `violation_probability(q: Question, answer: dict) -> float`: noul → `answer["noul"]` if `when_true` else `1 - answer["noul"]`; choice → sum of `answer["probabilities"][o]` over `violation.options`; score → sum of `answer["probabilities"][str(i)]` for `i >= at_or_above`.
  - `@dataclass(frozen=True) Finding(rule_id: str, source: Literal["check","decider"], item_id: str, p_violation: float | None, status: Literal["violation","clear","uncertain"])`
  - `@dataclass(frozen=True) Verdict(action: Action, rule_id: str | None, message: str, confidence: float, uncertain: bool, findings: tuple[Finding, ...])`
  - `decide(pack: Pack, tool: str, check_results: Mapping[str, bool | None], answers: Mapping[str, dict]) -> Verdict`
- Algorithm (pins the policy, write it exactly):
  1. Check `True` → violation, p=1.0; `False` → clear; `None` → uncertain.
  2. Question: p = `violation_probability`; `p >= q.hi` → violation; `p <= q.lo` → clear; else uncertain. A question with no answer → uncertain.
  3. If any violation: pick the rule with the most severe `on_violation` (deny > confirm > guide), ties → highest p, then rule order. `action = on_violation`, `message = rule.remedy`, `confidence = p` of the firing finding, `uncertain=False`.
  4. Else if any uncertain: `action="confirm"`, `uncertain=True`, `rule_id` = the uncertain finding with p closest to 0.5 (checks with None count as 0.5), `message = f"Needs a human look: {rule.text}"`, `confidence = 1 - 2*min(p, 1-p)` of that finding.
  5. Else `action="proceed"`, `rule_id=None`, `message=""`, `confidence = min(1 - p)` over questions (1.0 if none), `uncertain=False`.

- [ ] **Step 1: Write failing tests:** `test_violation_probability_each_type`; `test_check_violation_beats_clear_questions`; `test_severity_order` (guide + deny violations → deny); `test_uncertain_band_goes_to_confirm` (p=0.5 with lo .2 hi .8); `test_unknown_check_is_uncertain`; `test_all_clear_proceeds_with_min_confidence`; `test_missing_answer_is_uncertain`.
- [ ] **Step 2–4:** FAIL → implement → PASS. **Step 5:** Commit `feat: decision table`.

### Task 10: Compiler — cases, tuning, report, pipeline, CLI `compile`

**Files:** Create `src/bylaw/cases.py`, `src/bylaw/compiler/{generate,tune,report,pipeline}.py`, `src/bylaw/cli.py`, `tests/test_cases.py`, `tests/test_tune.py`, `tests/test_pipeline.py`

**Interfaces:**
- Produces:
  - `Case(id: str, tool: str, args: dict, context: dict, conversation: list[tuple[str,str]], expected: Action, rule_id: str | None, tags: list[str], source: str)`; `load_cases(path) -> list[Case]`; `save_cases(cases, path)` (jsonl).
  - `question_label(case: Case, q: Question | QuestionDraft) -> bool | None`: `True` if `case.rule_id == q.rule_id and case.expected != "proceed"`; `False` if `case.expected == "proceed"`; else `None` (excluded).
